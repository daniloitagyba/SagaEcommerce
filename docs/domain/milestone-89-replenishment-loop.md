# Milestone 89: The Replenishment Loop Closes

## Scope

`WarehouseReplenishmentNeeded` has been emitted, durably, since Milestone 73 - and Milestone 73 said so explicitly: "nothing in this lab consumes it yet; the event is emitted durably, and the consumer is somebody else's milestone." Sixteen milestones later, this is that milestone. The event carries exactly what a consumer needs (which SKU, which warehouse, how far below the reorder point) and nothing has ever read it.

The natural consequence of that gap is also worth naming: Milestone 74's backorder release path (`ReleaseBackordersAsync`, the FIFO queue a shopper waits in when a SKU can't be covered) has only ever been exercised by *manually* producing a restock command in tests and demos - there has never been a real, in-system cause that makes a restock happen on its own. This milestone gives it one.

## Design

**A purchase order is this lab's stand-in for "a human or a supplier's system now knows to send more stock."** `PurchaseOrder` is a small state machine - `Requested` when the signal arrives, `Received` once its lead time elapses - not a queue or a workflow engine, because the actual domain event here is genuinely that simple.

**`ReplenishmentRequestProcessor` consumes the signal and requests enough to matter, not merely enough to clear the alert.** A purchase order sized to bring stock back to exactly the reorder point would cross that same threshold on the very next sale - `TargetMultiplier` (default 3) sizes it to reach `ReorderPoint × TargetMultiplier` instead, so the warehouse doesn't immediately re-trigger the signal it just answered. Idempotent the same way every other consumer in this codebase is: an inbox row keyed on the event's own id, added to `WarehouseReplenishmentNeeded` in this same milestone specifically because nothing needed one while nothing consumed the event.

**`PurchaseOrderReceivingSweeper` is the delivery truck - a lab-scale compression of a real supplier's lead time into something a session can watch happen**, the identical trade Milestone 73 already made for a boleto's due date (minutes instead of days) and Milestone 74 made for a backorder's own wait window. Single-sweeper via `pg_try_advisory_xact_lock`, the same reasoning `BackorderTimeoutSweeper` already established in this exact service: `FOR UPDATE SKIP LOCKED` already makes concurrent sweeps safe on its own, so the advisory lock exists only to stop every replica polling every tick, not to prevent a real race.

**The actual restock reuses Milestone 74's tested path wholesale, through the outbox, not an in-process shortcut.** When a purchase order's lead time elapses, the sweeper doesn't touch `WarehouseStock` directly - it queues an `InventoryRestockRequested` command on Inventory's own outbox, which `OutboxPublisher` reliably produces to `inventory.restock-requested.v1`, which Inventory's own existing consumer (`InventoryReservationMessageProcessor.ProcessRestockAsync`) picks back up. That handler already does everything a restock needs - the aggregate/warehouse-level stock increase *and* the FIFO backorder release - so this milestone adds no new stock-mutation logic at all; it adds a new, real *cause* for the existing one to fire. The indirection through Kafka (rather than calling the restock logic in-process) is deliberate: if the produce fails after the purchase order is already marked `Received`, the outbox row this milestone writes in the same transaction is still there for `OutboxPublisher` to retry, so a transient Kafka failure degrades to "retried a moment later," not "the purchase order says received and the stock never actually came back" - precisely the silent-loss shape this entire pass of milestones has been closing everywhere else it was found.

**`InventoryOutboxEventDispatcher` and `IInventoryEventPublisher` both gained a small, honestly-labelled new case**: Inventory producing a command it also consumes, something no other event in this service does (every other outbox entry is a *reply* to Orders, never a command to itself). The comment on both says so plainly rather than leaving a future reader to wonder why an "incoming" command type appears in an outgoing dispatcher.

## Verification performed

Same constraint as every milestone in this pass: no Docker here, so the Testcontainers-backed integration tests below compiled but were not run.

- **Full solution build**: 0 warnings, 0 errors.
- **The EF migration was generated by `dotnet ef migrations add`** against `InventoryDbContextFactory`'s design-time factory, the same no-live-database approach Milestones 82 and 87's own migrations used.
- **`PurchaseOrderTests`** (2 facts, pure - no database, run in this session): `Create` starts in `Requested`; `TryReceive` moves to `Received` exactly once and a redelivered receive is a no-op that doesn't move the timestamp.
- **`ReplenishmentTests`** (4 facts, Testcontainers-backed, written but not run in this session): a replenishment signal requests exactly `ReorderPoint × TargetMultiplier - AvailableQuantity`; a redelivered signal (same `EventId`) does not create a second purchase order; the receiving sweep leaves a purchase order alone before its lead time elapses; a due one is marked `Received` and queues an `InventoryRestockRequested` carrying the purchase order's own id as `OrderId` (there being no real customer order behind a replenishment restock) and the exact quantity requested.
- **`Services.ArchitectureTests`**: 86/86, up from 82 - the new types were picked up by the existing fitness functions, not exempted from them.
- **Not verified in this pass**: any of the above against a real Postgres or Kafka; the full loop (signal → purchase order → receiving sweep → outbox → produce → `ProcessRestockAsync` → stock increase → backorder release) observed end to end on a live cluster, which is the one thing this milestone's own motivating gap - a backorder release path that has only ever been exercised manually - most wants to see happen for real.

## What was deliberately not done

- **A real supplier integration, or even a plausible fake one.** `PurchaseOrderReceivingSweeper` always receives what was requested, on schedule, in full - no partial shipments, no backorders-on-the-purchase-order-itself, no supplier ever failing to deliver. A real replenishment system has all three; this one exists to close the loop from signal to restock, not to model a supply chain.
- **A policy for which SKUs get a purchase order raised automatically versus routed to a human for approval.** Every crossing raises one, unconditionally - a real operation would very likely want a spend threshold or a category-based rule above which a person signs off first.
- **Cancelling a purchase order.** Once requested, it is received; there is no path to decide a warehouse no longer needs what was already asked for (a demand forecast changing, a SKU being discontinued) - the mirror image of Milestone 81's cancellation work, not itself in scope here.
