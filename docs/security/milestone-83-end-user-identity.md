# Milestone 83: The Shopper Stops Being Self-Asserted

## Scope

Milestone 26 built *application* identity - which client is calling, proven by a JWT, backed by Keycloak. It was explicit about the boundary it was drawing: "which client is calling," not "which shopper is calling." Nine milestones of domain work (67 through 82) were then built on top of the half that was left for later: `customerId` has been a string the request body supplies since Milestone 7, and every route that touches an order trusts it.

An audit of every order-facing route found the concrete consequences:

- **`POST /orders`**: any caller holding `orders:write` places an order as any customer, spending that customer's loyalty tier discount, their per-customer coupon allowance, their payment risk history.
- **`GET /orders/{id}`, its gRPC mirror, and `GET /orders/{id}/history`**: any caller holding `orders:read` reads any order - full pricing breakdown, shipping address, event history - by guessing or enumerating a GUID.
- **`GET /orders/summary`**: the mass-disclosure version of the same gap - unpaginated beyond a `limit`, with no way to scope it to one customer even as an option. A plain `orders:read` token lists every customer's orders.
- **`POST /orders/{id}/returns`**: any `orders:write` caller returns *any* order and triggers *its* refund.
- **`POST /orders/{id}/fulfillment`**: the warehouse's endpoint, reachable by the same `orders:write` role a shopper's own token would need for checkout - including the route to `Cancelled`.
- **Storefront.Service**, the only path a browser has, authenticated to Orders.Api as *itself* (a confidential client's service-account token) and simply relayed whatever `customerId` the checkout request body carried. The security boundary Milestone 26 built was real; every request that mattered arrived on the trusted side of it regardless.

This milestone closes all of it: real end-user identity, an ownership check on every route above, an `orders:admin` role for the callers that legitimately need to cross that boundary, and the shopper's first self-service action - cancelling their own order - which had no route at all before this.

## Design

**`preferred_username`, not `sub`, is the verified identity.** `customerId` has been a human-readable string ("customer-42") since Milestone 7, threaded through coupons, loyalty tiers, and order history. Provisioning Keycloak users under those same usernames (`scripts/keycloak-configure-realm.sh`, which now creates a demo `customer-42` user) lets every existing consumer of `customerId` keep working unchanged - no parallel identity migration, no new column, nothing downstream even has to know this happened. `sub` (Keycloak's stable UUID) is a fallback for a token that carries no username, not the primary source. A system that needed collision-proof identity independent of a mutable username would make the opposite choice; this lab's existing `customerId` scheme is specifically why it doesn't have to.

**`CallerIdentity` is a plain record in `Orders.Application`, not `HttpContext` threaded through the use cases.** `Orders.Application` has an existing, enforced fitness function (`ApplicationDoesNotDependOnAnyInfrastructureFramework`) forbidding a dependency on `Microsoft.AspNetCore` - authorization decisions still need to reach into a handler, so `CallerIdentity(string? CustomerId, bool IsAdmin)` plus one method, `MayAccess(string? resourceCustomerId)`, is the entire vocabulary that crosses the boundary. `Orders.Api.Authorization.CallerIdentityExtensions.GetCallerIdentity(HttpContext)` is the only place that builds one, reading the two claims above.

**Reads check ownership after the fact; writes check it before any mutation.** For a read (`GetByIdAsync`, its gRPC mirror, `GetHistoryAsync`), the row has to be fetched to know whose it is regardless, so the check runs on the result and a non-owner gets exactly the same `404` a genuinely missing id produces - never `403`, so probing ids can't distinguish "not yours" from "doesn't exist." For a write, that ordering is wrong: `ReturnOrderHandler` now takes a `CallerIdentity` and checks it immediately after loading the order but *before* calling `Order.TryReturn` - a non-owner's request must never reach the mutation, even transiently, and reporting the rejection is cheap precisely because nothing happened yet.

**`AdvanceFulfillmentHandler.HandleSelfServiceCancelAsync` needed no locking to check ownership safely before mutating** - unlike an order's *status* (Milestone 81's `FOR UPDATE` fix), its `CustomerId` is set once at creation and never changes, so a plain prior read carries none of the same race risk. It fetches the order, checks `caller.MayAccess(order.CustomerId)`, and only then runs the existing compare-and-set through `IOrderStatusRepository.TryTransitionAsync` - reusing Milestone 81's machinery rather than duplicating it, restricted to a caller-specific predecessor set (`Created`, `Confirmed`, `Backordered`) that excludes `Picking` and `FulfillmentHold`: once the warehouse is acting on an order, or a human already needs to look at it, that call is fulfilment's, not the shopper's.

**`orders:admin` replaces neither `orders:read` nor `orders:write` - it satisfies both.** Orders.Api's policies now accept the admin role in place of either (`RequireRole("orders:read", "orders:write", "orders:admin")` and similarly for Write), so an admin token needs exactly one role to do everything a shopper's token can, plus what an admin-only route requires. `POST /orders/{id}/fulfillment` moved from `Write` to `Admin` outright - it is the warehouse's endpoint, able to move *any* order through *every* fulfilment state, which a shopper token should never be able to do even to their own order.

**Storefront.Service forwards the shopper's own bearer token instead of minting one.** Both order-creation paths - `StorefrontEndpoints.CheckoutAsync` (the cart-driven flow) and `ProxyEndpoints`' direct `/api/orders` passthrough (kept for k6/Pact/the README quickstart) - used to call `KeycloakTokenProvider.GetTokenAsync()` and inject a client-credentials token authenticating as Storefront itself, then relay whatever `customerId` the request body asserted. They now require an inbound `Authorization` header and forward it verbatim; Orders.Api validates it directly, the same JWKS-backed check every other caller goes through. One fewer trusted intermediary - not a second-hand claim Storefront re-signs, the shopper's own token, checked by the service that owns the data. `KeycloakTokenProvider` is deleted outright, not left as a fallback: nothing calls it any more.

**A demo shopper needs a way to authenticate without a browser.** `scripts/keycloak-configure-realm.sh` provisions `orders-storefront` as a public client (`publicClient: true`, PKCE via `pkce.code.challenge.method: S256`, no secret - a browser can't keep one) for the real authorization-code flow a production frontend would use. This lab's non-interactive smoke/k6/chaos scripts have no browser to drive that redirect through, so the same client also enables direct access grants (Resource Owner Password Credentials) - explicitly not a production-realm choice, called out as such in the script's own comment, and scoped to exactly the one demo user (`customer-42`, `KEYCLOAK_DEMO_CUSTOMER_PASSWORD` in `.env`) it provisions. `scripts/keycloak-get-shopper-token.sh` is the ROPC equivalent of the existing `keycloak-get-token.sh`, fetching a real shopper token instead of a service-account one.

**`GET /orders/summary` gained a customer filter and keyset pagination in the same pass**, since fixing the ownership gap without also bounding an admin's cross-customer listing would have left the mass-disclosure half of the same finding half-closed. A non-admin caller is always scoped to their own `customerId`; an admin may pass one explicitly or omit it for the old unfiltered listing. Pagination is a cursor (`{ProjectedAt}_{OrderId}`, opaque to the caller, returned as `nextCursor` when a page came back full) rather than an offset - the projection this reads from grows continuously, and an offset would skip or repeat rows under concurrent inserts the way a cursor anchored to a specific row doesn't. The keyset predicate deliberately avoids `Guid.CompareTo()` inside the `WHERE` clause (not every EF provider translates it to SQL, and a query that throws on page two is worse than pagination that is merely imprecise across a same-millisecond tie) in favor of plain equality/inequality, which is always translatable; the `ORDER BY` itself orders by `OrderId` with no such restriction, since that's a plain SQL `ORDER BY`, not a method-call translation.

## Verification performed

Same constraint as Milestones 81-82: no Docker here, and this milestone specifically cannot be fully verified without one - there is no live Keycloak to mint a real token against, so nothing below exercises the actual JWT validation, PKCE flow, or realm provisioning script end to end. That gap is larger for this milestone than the previous two, and is the honest state of it.

- **Full solution build**: 0 warnings, 0 errors, across all seven services plus every test project.
- **`Orders.UnitTests`**: 196/196 passing, including 6 new `CallerIdentityTests` covering every branch of `MayAccess` (owner, non-owner, admin-with-no-identity, non-admin-with-no-identity, a null resource owner, and that comparison is ordinal - a token claim, not a display string to fold case on).
- **`Storefront.UnitTests`**: 7/7 passing, `CheckoutEndpointTests` rewritten for the new signature - a missing `Authorization` header now asserts `401` before any dependency is called, and the happy-path test asserts the *forwarded* header reaches Orders.Api verbatim and that the request body carries no `customerId` at all any more.
- **`Orders.ArchitectureTests`** (85/85) and **`Services.ArchitectureTests`** (80/80) both pass unchanged - `CallerIdentity`'s placement in `Orders.Application` was checked against the existing layering fitness functions, not exempted from them.
- **`scripts/keycloak-configure-realm.sh` and `scripts/keycloak-get-shopper-token.sh`**: both pass `bash -n` syntax checking. Neither has been run against a live Keycloak.
- **Not verified in this pass, and the largest gap of the three identity-adjacent milestones**: the PKCE/ROPC flows against a real Keycloak; the realm provisioning script's idempotency on a second run; `preferred_username` actually arriving in a token the way this milestone assumes; the gRPC ownership check; the `/orders/summary` cursor across a real multi-page dataset; and every existing script that authenticates as `orders-api-clients` (now `orders:admin`) continuing to work - traced through by reading (`coupon-redemption-concurrency-test.sh`'s per-request varying `customerId` specifically depends on the admin override still honoring a body-supplied value), not executed.

## What was deliberately not done

- ~~**Cart ownership.**~~ **Resolved by Milestone 84.** `cartId` was a client-supplied opaque string with no verified owner - the enumeration surface that let one shopper read or clear another's cart - at the time this milestone shipped, deliberately: Cart.Service had no authentication at all yet to derive an owner from. Milestone 84 gave it that authentication and derived the cart's key from the shopper's own identity, closing the gap named here.
- **Revoking or migrating existing non-Keycloak-backed `customerId` values.** Every `customerId` this lab has ever seeded or generated (`customer-42`, `race-customer-{i}`, k6's synthetic ids) keeps working exactly as before under an admin token; only a *non-admin* caller is now bound to their own verified identity. No backfill, no forced re-authentication of historical data.
- **A UI.** Nothing in this lab has a browser-based frontend to actually drive the authorization-code+PKCE flow through; `orders-storefront`'s standard flow is provisioned and ready for one, unexercised.
